# 后端核验记录：部分成立的判断

记录日期：2026-10-04。基准：`b28699f85639ece8a8606bac044d9abbd4a3272f` 上的当前未提交工作区。

本文件记录额外审查摘要中“事实存在，但推论过重、适用范围有限或简化有前提”的判断。每项分别说明成立的部分、需要修正的部分和后续决策条件。已经确认的具体成本与缺口见[成立的发现](backend_confirmed_findings.md)，完整背景见[原审查报告](backend_code_complexity_and_redundancy_report.md)。

## 1. 判断清单

| 编号 | 原判断主题 | 核验后的准确表述 |
|---|---|---|
| P01 | TTS 双轨都是冗余 | 两种模式有维护成本，也有不同且仍被使用的契约 |
| P02 | Private 内存缓存完全无价值 | 不避免全文件校验，但仍复用音频 bytes |
| P03 | RLock 令所有请求全面串行 | 同一 store 的存储阶段串行，上游合成可并行 |
| P04 | 文件备份和恢复属于过度设计 | 有额外成本，也保护数据库与文件的一致性 |
| P05 | 五重控制都是重复锁，Redis 必然失配 | 控制目标不同；单进程可讨论减少跨进程控制 |
| P06 | 硬编码 1000 后全部永久 503 | 默认值可配置；新存档 507，已有缓存仍可用 |

| P13 | 密码锁串行登录就是缺陷 | 降低密码计算吞吐量，同时限制 Argon2 内存并发 |

## 2. 成立范围与决策条件

### P01：TTS 存储双轨增加维护成本，但并非全部冗余

**成立部分**：Legacy 和 Private 各有存储、历史、目录和淘汰规则，需要分别维护和验证。

**需要修正**：每次业务调用只选择一种实现，共同生成流程已集中到 `TTSService`。Legacy 提供共享音频、旧 key 重播和 TTL；Private 提供 owner 隔离、原音频与时间轴共用、播放 LRU 和 unavailable 状态。Legacy 当前仍是默认模式，不能认定为无用残留；文件总行数也不能直接当作可删除冗余行数。

**决策条件**：先明确是否长期支持匿名模式、旧 key 重播、旧数据保留及回滚窗口，再定义 Legacy 退出门槛。已有清理脚本不负责将匿名数据映射为账号数据。

**证据**：[存储选择](../src/app/services/tts_storage.py#L69)、[共同业务流程](../src/app/services/tts_service.py#L17)、[默认配置](../src/app/config.py#L115)、[旧 key 重播测试](../tests/test_storage_integrity.py#L57)。

### P02：Private 内存层不能避免文件读取，但仍有有限用途

**成立部分**：暖命中仍读取完整文件并校验 SHA-256，见成立文档 C01。

**需要修正**：缓存复用已有的不可变 `bytes`，减少重新分配；文件读取可能命中操作系统缓存。“彻底无价值”和“每次都物理读盘”均超出证据。

**决策条件**：测量音频大小、重复播放、哈希成本和内存驻留收益；决定是否必须每次立即检测同尺寸、保留 mtime 的损坏。放宽校验会改变现有检测能力。

**证据**：[暖命中实现](../src/app/services/private_tts_storage.py#L211)、[保留时间戳的损坏测试](../tests/test_private_tts_storage.py#L146)。

### P03：RLock 覆盖较大的存储范围，但不覆盖全部请求过程

**成立部分**：同一 Private store 的 get、put、touch、历史列表和删除共用一个 RLock。文件读取、哈希、fsync、事务及部分清理位于锁内，不同用户的存储操作会相互等待。

**需要修正**：上游合成发生在存储 get 返回之后、save 之前，处于该锁之外。所谓只读路径也可能更新内存缓存、播放时间或 unavailable 状态。锁范围不能扩大表述为“全系统所有请求全面串行”。

**决策条件**：先减少锁内重复工作并测量等待时间。缩锁或改细锁时仍需协调内存缓存、全局容量和文件删除。

**证据**：[get 锁范围](../src/app/services/private_tts_storage.py#L194)、[put 锁范围](../src/app/services/private_tts_storage.py#L256)、[合成调用顺序](../src/app/services/tts_service.py#L31)。[跨用户并行测试](../tests/test_private_tts_api.py#L189)要求两个用户同时进入模拟上游合成，并验证同用户请求合并。

### P04：临时文件、备份与恢复有成本，也有具体保护对象

**成立部分**：写入使用临时文件和 fsync；替换已有文件时保留备份；启动恢复会扫描文件和核对数据库状态。

**需要修正**：SQLite 回滚不能撤销文件 replace。临时文件防止发布半文件，备份用于恢复替换前的原音频，恢复逻辑依据已提交 digest 选择匹配副本。备份不是每次把音频复制写入两遍。原音频可能来自付费生成，GET 也不自动重新合成。

**决策条件**：先明确原音频保留和耐久要求，再评估写入及启动耗时。现有故障注入测试证明保护有用途，但不是硬件断电测试，也不证明绝对耐久。

**证据**：[写入协议](../src/app/services/private_tts_storage.py#L286)、[启动恢复](../src/app/services/private_tts_storage.py#L399)、[失败替换测试](../tests/test_storage_integrity.py#L150)、[重启备份恢复测试](../tests/test_storage_integrity.py#L205)、[Windows 占用恢复测试](../tests/test_storage_integrity.py#L296)。

### P05：LLM 有多项控制，但它们保护不同资源

**成立部分**：缓存未命中的生成路径经过本地键锁、Redis 同键锁、SQLite 容量预留、Redis 加权额度和提供商信号量；默认 Docker 只启动一个 worker。

**需要修正**：本地和 Redis 锁分别协调进程内与跨进程的同键请求；容量预留避免多个不同键同时为最后一个存储位置付费；额度控制分钟和日消费；信号量限制上游并发。容量和配额预留不是互斥锁。使用 Redis 也不等于部署了 Redis 集群。

**部署边界**：development/test 未配置 Redis 时会跳过分布式锁和额度控制；production 无条件要求 Redis，增加了部署依赖。源码只能证明默认配置，不能证明实际部署环境。

**决策条件**：明确支持一个应用进程还是多个外部进程，并决定消费额度是否需要跨重启保留。可以单独讨论减少分布式同键锁；不能据此一并取消存储容量、消费额度和上游并发保护。预留保存协议缺口见成立文档 C07。

**证据**：[路由控制顺序](../src/app/api/explain.py#L70)、[容量预留](../src/app/services/explain_service.py#L263)、[额度控制](../src/app/services/llm/quota.py#L90)、[Redis 锁](../src/app/services/llm/quota.py#L137)、[生产限制](../src/app/config.py#L158)、[单 worker](../Dockerfile#L40)。

### P06：讲解容量缺少释放路径，但不是达到 1000 后全系统永久 503

**成立部分**：讲解存档没有自动淘汰、TTL 或应用内删除入口，容量用尽后新增存档会持续受限，见成立文档 C05。

**需要修正**：1000 是可配置默认值。容量不足映射为 **507**，已有缓存在新增预留前返回 **200**；已有追问不新增讲解记录。路由在付费调用前检查容量，预留租约也有独立到期时间。

**其他故障边界**：POST 缓存命中仍先获取 Redis 锁，已配置 Redis 故障时也可能返回 503；这是协调服务故障，与记录上限不同。

**决策条件**：定义存档保留和释放政策，提供可恢复容量的操作；不要用直接删除容量保护代替生命周期设计。

**证据**：[默认上限](../src/app/config.py#L126)、[缓存优先返回](../src/app/api/explain.py#L75)、[异常响应](../src/app/main.py#L131)、[满库测试](../tests/test_explain.py#L439)。

### P07：gateway 是薄包装，是否合并取决于实际收益

**成立部分**：当前 gateway 约 9 行，调用 provider 后将模型 ID、模式 ID 和版本包装成四元组，没有额外分发逻辑。

**需要修正**：该层被生成服务实际调用，不是死模块。薄层本身不证明高危架构缺陷。已解析的模型信息再次包装和拆包有简化空间，但收益较小。

**决策条件**：统一生成入口的参数和返回契约；若不需要独立调用接缝，再合并。同步维护测试 mock、缓存版本和追问模型语义。

**证据**：[gateway](../src/app/services/llm/gateway.py#L5)、[生成服务调用](../src/app/services/explain_service.py#L217)、[调用契约测试](../tests/test_explain.py#L421)。

### P08：404 墓碑会增加记录，但有准入限制和真实乱序保护

**成立部分**：不存在的有效 UUID 会产生永久空墓碑；没有专门的墓碑配额或回收窗口，见成立文档 C06。

**需要修正**：接口需要登录和 CSRF 校验，受请求限流和 `DB_MAX_BYTES` 限制。不是任意匿名无效请求无限增加数据。墓碑还阻止迟到 POST 将已取消文章创建出来：浏览器 abort 不保证服务器停止提交。

**决策条件**：明确允许的创建重试窗口和删除确认语义，选择回收、限额或紧凑删除记录方案。任意到期删除墓碑可能让旧 POST 再次创建文章。

**证据**：[墓碑写入](../src/app/services/article_service.py#L79)、[登录依赖](../src/app/api/articles.py#L11)、[CSRF 与身份测试](../tests/test_articles.py#L85)、[乱序测试](../tests/test_articles.py#L126)、[数据库容量限制](../src/app/services/database.py#L29)。

### P09：文章路径特例和请求体预缓冲存在，但不能直接认定为缺陷

**成立部分**：RequestLimits 硬编码文章路径，为其设置 4 MiB 上限，并在调用应用前收集请求体，通过 `b"".join(chunks)` 向下游交付完整内容。

**需要修正**：该逻辑在 JSON 解析前限制实际字节数、chunked 上传和慢速请求。当前文章接口接受完整 JSON，Starlette 的 JSON 读取本身也会缓冲正文；不能把 ASGI receive 包装直接认定为“绕过框架导致缺陷”。

**决策条件**：可将路径特例和限额提取为清晰的常量。若改为流式读取，需明确是否仍在业务解析前拒绝超限和超时请求，并测量实际内存峰值。

**证据**：[大小限制](../src/app/api/limits.py#L80)、[收集与交付](../src/app/api/limits.py#L94)、[文章请求模型](../src/app/schemas/articles.py)。

### P10：迁移时机和事件时间可以统一，但不同字段不应强行同格式

**成立部分**：三套初始化生命周期存在，见成立文档 C08。讲解仍使用本地 naive 时间，账号和新播放记录使用 UTC 时间，事件时间约定没有完全统一。

**需要修正**：UTC 日期桶用于按日统计，epoch 秒用于到期判断，和事件时间承担不同职责。`strftime` 与 Python UTC helper 也可以生成同类绝对时间；函数名称不同不等于时间语义错误。

**决策条件**：优先统一绝对事件时间并迁移旧值，保留日期桶和到期字段的独立语义。跨时区排序不能直接依赖混存时间的文本顺序。

**证据**：[绝对时间 helper](../src/app/services/timestamps.py#L4)、[讲解时间默认值](../src/app/services/explain_service.py#L48)、[UTC 用量日期桶](../src/app/services/explain_service.py#L408)。

### P11：异常映射有相似代码，运行时核心已经共用

**成立部分**：TTS 和 LLM 各有异常类型与 provider 错误映射，包含相似的超时、状态码和网络异常处理。

**需要修正**：两者适配的上游异常来源和公开 HTTP 响应不同。TTS 还处理 aiohttp 与 SDK 异常；LLM 有自己的错误契约。`request_deadline` 和 `llm_request_deadline` 已共用 `_deadline`，两类并发入口已共用 `_upstream_slot`，并非完整复制。

**决策条件**：只提取真正相同的小范围状态处理；保留业务错误类型、配置、提示和并发 namespace，不为减少少量相似代码引入更复杂的泛型异常框架。

**证据**：[LLM 映射](../src/app/services/errors.py#L63)、[TTS 映射](../src/app/services/errors.py#L92)、[共用运行时](../src/app/services/runtime.py#L28)、[HTTP 响应差异](../src/app/main.py#L82)。

### P12：配置数量较多，GLM 默认禁用但不是死存根

**成立部分**：Settings 有 70 个大写配置属性，覆盖账号、邮件、OAuth、模型、消费额度、并发与存储；多功能范围增加了维护成本。

**需要修正**：静态核验中 70 个属性均在配置模块之外被运行时代码引用。GLM 有模型配置、四种模式和固定提供商 HTTP 调用路径，显式开关使它可到达。配置数量也不代表所有选项都必须手工填写。

**外部能力边界**：GLM 默认不在 allowlist，额外开关默认关闭；示例配置说明其生产 API 契约尚未验证。模拟参数测试不能证明真实上游能力，本次未调用上游验证。

**决策条件**：按实际支持的产品功能与部署形态减少配置。删除模型前明确是否继续支持显式启用，避免把默认禁用等同于不可达代码。

**证据**：[Settings](../src/app/config.py#L48)、[GLM profile](../src/app/services/llm/registry.py#L22)、[调用实现](../src/app/services/llm/providers.py#L65)、[启用限制](../src/app/services/llm/registry.py#L62)、[示例说明](../.env.example#L56)。

### P13：密码计算串行化限制吞吐量，也限制内存并发

**成立部分**：`hash_password()` 和 `verify_password()` 共用全局 `_hash_lock`，同进程的密码哈希与验证会排队，影响登录、注册和重置密码中的计算阶段。

**需要修正**：锁的明确目的为限制单 worker 的内存使用。当前安装的 Argon2 默认 profile 每次计算约需 64 MiB；线程池执行不等于限制密码计算资源。锁没有把全部登录业务串行化，也不能在未测量负载时直接认定为缺陷。

**决策条件**：根据容器内存、登录峰值和响应目标测量等待时间，再决定保持串行或使用有限并发。保留未知账号与无密码账号的 dummy hash 行为。

**证据**：[密码服务](../src/app/services/passwords.py#L7)、[登录路径](../src/app/services/auth_service.py#L130)。64 MiB 参数来自核验时本地安装的 argon2 `RFC_9106_LOW_MEMORY`，应在依赖升级后重新确认。

## 3. 验证记录与后续使用

2026-10-04 的后端回归基线为 **462 passed，2 个依赖弃用警告**；命令和证据范围见成立文档第 3 节。
